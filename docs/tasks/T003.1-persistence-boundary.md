# T003.1 — Typed Data / Persistence Boundary

**Status:** Proposed architecture/specification  
**Scope:** Persistence architecture and mapping only  
**Explicitly out of scope:** database migrations, ORM/query-layer implementation, API, UI, connectors, AI/ML

## 1. Findings

1. `packages/domain/src/index.ts` is the current canonical contract. The persistence boundary must preserve its distinctions rather than flattening them into generic records.
2. `packages/database` contains no implementation yet. No existing schema, ORM, migration tool, or live database contract constrains this design.
3. Existing architecture decisions establish a modular monolith and PostgreSQL with typed relational graph records. This specification therefore uses PostgreSQL as the V1 persistence target and keeps graph relationships relational.
4. `SourceIdentifier` is not an eGovTrace identity. It must be stored as a separately addressable assertion with a source-system namespace.
5. `TemporalValidity` plus `observedAt` requires both valid-time and observation/recording metadata. A single mutable “current state” column would lose history.
6. `ProvenanceReference`, relationship evidence, and source references are queryable domain concepts. JSON-only storage would make the required evidence and lineage queries unreliable.
7. The current `Payment` type contains a `financialState` union. Persistence must still store obligation, disbursement, and settlement as distinct state records; the union must not become an overwrite-based lifecycle.
8. `UNAVAILABLE`, `NOT_OBSERVED`, and `ABSENT` are distinct domain values. Missing rows or `NULL` cannot stand in for any of them.
9. The current context does not decide the ORM/query library, internal ID encoding, evidence-object storage provider, retention schedule, or production authorization model. These remain explicit unresolved decisions.

### 1.1 Required-capability review

The proposed shape explicitly supports each T003.1-R1 requirement:

| Requirement | Boundary in this specification |
|---|---|
| Domain entities | `domain_entity` plus typed subtype tables and the `DomainEntity` mapping |
| Separate source identifiers | `source_system` and `source_identifier`; source keys never serve as domain keys |
| Historical/temporal state | append-only `state_version` with valid, observed, recorded, and snapshot times |
| Provenance | queryable `provenance_record`, parent edges, and typed attachments |
| Relationship assertions | independent `relationship_assertion` records with typed endpoints and status |
| Supporting evidence | `evidence` records plus relationship-to-evidence links |
| Financial lifecycle separation | independent `financial_state_record` rows for obligation, disbursement, and settlement |
| Immutable source snapshots | immutable `source_snapshot` retrieval/observation boundaries with hashes where available |
| Source/identifier registry | `source_system` registry and namespaced `source_identifier` records |
| Idempotent mutations | `idempotency_record` and deduplicated ingestion/outbox consumers |
| Optimistic concurrency | explicit workflow `record_version`/expected-version checks |
| Transaction boundaries | source-ingestion, domain-command, and projection transactions |
| Outbox/event publication | transactional `outbox_message` records consumed at least once |
| Separate public read models | allowlisted projection tables/schemas with canonical and policy versions |
| Unavailable source data | explicit availability/status values; missing rows and `NULL` are not negative facts |

This is a conceptual contract only. It does not prescribe table DDL, SQL, migrations, an ORM, or repository code.

## 2. Proposed Persistence Architecture

### 2.1 Logical layers

The database is one PostgreSQL persistence boundary inside the modular monolith, with these logical layers:

- **Canonical entity layer:** eGovTrace entities and subtype attributes.
- **Source observation layer:** source identifiers, snapshots, source references, and observed payload metadata.
- **Assertion/history layer:** temporal states, relationship assertions, event assertions, and supersession/correction links.
- **Provenance layer:** source, normalization, derivation, AI assistance, human adjudication, and synthetic-fixture lineage.
- **Financial layer:** independently persisted obligation, disbursement, and settlement records.
- **Workflow/audit layer:** human decisions, optimistic versions, idempotency records, audit entries, and an outbox.
- **Projection layer:** separately materialized public/read projections; projections do not replace assurance records.

The database is authoritative for eGovTrace's normalized records, relationships, provenance, workflow state, and derived projections. It is not authoritative for the underlying government source records. Source systems remain authoritative for their own records.

### 2.2 Relational shape

Use typed relational tables, not a single polymorphic JSON document table:

- `domain_entity`: common eGovTrace identity, entity type, lifecycle metadata, and classification.
- One subtype table per current domain entity where attributes differ materially: `institution`, `office`, `person`, `official`, `authority`, `legal_instrument`, `project`, `budget`, `procurement`, `bidder`, `contractor`, `contract`, `payment`, `evidence`, and `government_event`.
- `source_system`: source/authority registry entry, namespace, authority metadata, availability metadata, and lifecycle status.
- `source_identifier`: namespaced source-system identifier attached to an entity, event, evidence record, or financial record; it is not an eGovTrace ID.
- `source_snapshot`: immutable retrieval/observation boundary, including retrieval time, source reference, content hash where available, access classification, and synthetic marker.
- `provenance_record`, `provenance_parent`, and typed attachment tables for entity, state, relationship, event, evidence, and projection lineage.
- `state_version`: append-only temporal state assertions.
- `relationship_assertion` plus endpoint, evidence, and provenance join tables.
- `financial_state_record` plus evidence/provenance and explicit bridge records.
- `idempotency_record`, `audit_log`, `outbox_message`, and explicit workflow `record_version` columns for mutation safety.

JSON may be retained as source payload or unmapped source attributes for reproducibility, but it is not the queryable representation of domain identity, relationship basis, status, validity, provenance, or financial state.

### 2.3 Read models

Canonical records and assurance data remain the source of truth for eGovTrace. Public projections are generated into separate projection tables or schemas with an allowlisted field contract. Public queries must not traverse raw assurance tables and then rely on application filtering to hide restricted evidence.

Projection rows carry the source canonical version and projection policy version used to produce them. A projection may be unavailable or stale; that condition must be observable and must not be represented as a negative source fact.

## 3. Domain-to-Persistence Mapping

### 3.1 Common `DomainEntity` envelope

| Domain field | Persistence representation |
|---|---|
| `id` | `domain_entity.id`, an opaque generated eGovTrace key; never a source record ID |
| `entityType` | constrained `domain_entity.entity_type` |
| `sourceIdentifiers` | rows in `source_identifier`, linked by typed owner reference |
| `provenance` | rows in `provenance_record` and `provenance_attachment` |
| `stateHistory` | rows in `state_version`; no historical state is overwritten |

Subtype tables hold scalar fields and foreign keys. Domain references become foreign keys to `domain_entity` plus an entity-type constraint at the repository/domain boundary. The database must reject dangling references.

### 3.2 Entity mapping

| Domain type | Persistence attributes and required distinctions |
|---|---|
| `Institution` | name, institution type, and versioned active/inactive state |
| `Office` | institution FK, name, and versioned active/inactive state |
| `Person` | display name and versioned active/inactive state; no inferred identity merge |
| `Official` | person FK, office FK, role, appointment validity, and appointment state history |
| `Authority` | granting institution, holder reference, scope, validity, optional legal instrument, and state history |
| `LegalInstrument` | title, type, issuer, effective validity, and legal state history |
| `Project` | name, institution, optional office/program references, and project state history |
| `Budget` | optional project, fiscal year, amount, revision, and append-only revision lineage |
| `Procurement` | optional project, institution, optional source procurement reference, and procurement state history |
| `Bidder` | procurement FK, legal name, and bidder status history |
| `Contractor` | legal name, registration source identifiers, and contractor state history |
| `Contract` | optional procurement/project, contractor FK, value, and contract state history |
| `Payment` | optional contract/project and a state-specific view over independent financial-state assertions; obligation, disbursement, and settlement are never overwritten into one lifecycle row |
| `Evidence` | evidence type, source reference, capture time, content hash, assertion kind, confidence, access classification, and availability state |
| `GovernmentEvent` | event type, occurred/recorded times, object reference, actors, authority/legal basis, financial value, location, related events, evidence references, source references, classification, status, assertion kind, confidence, and optional validity |

`GovernmentEvent` is the normalized temporal spine, but it does not certify that an event physically occurred. Its status and assertion kind remain persisted as supplied/derived, with evidence and provenance links.

### 3.3 Value objects and references

- `Money` is stored as a fixed-precision numeric amount plus an explicit currency code. Binary floating-point storage is prohibited for persisted monetary values.
- `Location` is stored with country/administrative/locality fields and optional geospatial coordinates/precision metadata. Coordinates do not prove project or identity continuity.
- `DomainReference` is an explicit `(entity_type, entity_id)` reference. It is not a free-form source identifier.
- Enum values are constrained at the persistence boundary or represented by versioned lookup values where future source vocabulary expansion is expected. Unknown source values are quarantined or mapped to an explicit unavailable/unknown state; they are not silently coerced.

## 4. Primary Keys and Source Identifiers

### 4.1 eGovTrace primary keys

All persisted domain records receive an opaque generated eGovTrace primary key. The implementation may choose UUID/UUIDv7/another sortable opaque key in T003.2, but the key must be independent of source identifiers and must not encode source-system meaning.

Every dependent table uses its own stable primary key where it represents an assertion, snapshot, provenance record, evidence link, state version, or workflow action. A source record can therefore produce multiple observations and revisions without key reuse.

### 4.2 Source identifier model

`source_identifier` contains at minimum:

- `source_system_id`
- optional `namespace`
- `source_record_id`
- owner type and owner eGovTrace ID
- first observed and last observed timestamps
- source snapshot reference
- provenance reference

The uniqueness boundary is `(source_system, namespace, source_record_id, owner/context)` as defined by the source registry. The same string from two systems is not the same identifier. A source identifier must never be used as an eGovTrace primary key.

Source identifiers can be attached to entities, events, evidence, and financial-state records. A source identifier collision or reassignment is retained as a contradiction/new observation, not silently merged.

## 5. Temporal and History Strategy

Use append-oriented valid-time history with recording metadata:

- **Valid time:** `valid_from` and optional `valid_to` from `TemporalValidity`.
- **Observation time:** when the source says the state/event was observed, such as `observedAt` or `occurredAt` where applicable.
- **Recorded time:** when eGovTrace persisted the assertion.
- **Snapshot time:** when the source payload was retrieved/captured.

A `state_version` row is immutable after recording except for administrative correction metadata. A later source observation creates a new row and may mark an earlier assertion as superseded or contradicted. It does not update the earlier validity or replace its provenance.

The query layer may expose a current/as-of view, but the view is derived. It must support both:

- “What did the source/assertion say at time X?”
- “What did eGovTrace know and record at time Y?”

Temporal overlap rules are domain-specific. Do not add a universal exclusion constraint until each state family defines whether overlapping assertions are valid, contradictory, or concurrent observations.

## 6. Provenance Persistence Strategy

Provenance is a first-class, queryable graph:

- `provenance_record` stores kind, method, recorded time, actor/process metadata, and optional source reference.
- `provenance_parent` stores parent provenance edges, preserving transformation history.
- Typed attachment rows link provenance to entities, state versions, relationship assertions, evidence, events, financial records, and projections.
- `source_snapshot` stores immutable retrieval context and content hash where available.
- Evidence content may live in an object store later, but its database metadata, hash, classification, custody events, and provenance remain in PostgreSQL.

`AI_ASSISTANCE` is stored as derived provenance and cannot change an assertion into a source fact. `HUMAN_ADJUDICATION` records the human action and basis; it does not erase the source observation. Synthetic fixtures remain explicitly marked synthetic.

Minimum query guarantees:

- given any material claim/assertion, return its direct and transitive provenance;
- given an evidence item, return its source snapshot, retrieval/capture history, and derived consumers;
- given a projection row, return the canonical version and policy version used to produce it.

## 7. Relationship Assertion Persistence

`relationship_assertion` is an independent append-oriented record with:

- eGovTrace assertion ID;
- relationship type;
- typed `from` and `to` endpoints;
- assertion kind (`DERIVED_RELATIONSHIP` or `CLAIM`);
- confidence and status;
- valid-time interval;
- recorded/observed timestamps;
- source identifier and source snapshot where applicable;
- provenance attachment;
- normalized relationship-basis rows; and
- supporting evidence rows.

`basis` and `supportingEvidenceIds` are separate persisted sets. A basis such as `COMMON_ATTRIBUTE`, `SEMANTIC_MATCH`, or `TEMPORAL_ALIGNMENT` never becomes identifier proof. Identity confirmation requires the domain rule already present in `isExplicitlyConfirmedIdentity`: supported status plus direct source reference and explicit identifier reference. Persistence must not upgrade a weak assertion by aggregation.

Rejected and unresolved assertions remain queryable. A replacement assertion is a new row linked as a superseding or contradictory assertion. No relationship row may imply corruption, legal liability, or wrongdoing solely because it exists or has high confidence.

## 8. Financial-State Persistence

Persist financial records by state, not as one mutable “paid” record. Each listed row is an independent financial-state assertion and can have a different source identifier, evidence, provenance, validity, and availability status:

- `financial_state_record(state = OBLIGATION)`
- `financial_state_record(state = DISBURSEMENT)`
- `financial_state_record(state = SETTLEMENT)`

Each record has its own source identifiers, amount/currency, status, valid/observed/recorded times, provenance, evidence, and optional links to project/contract. A relationship or explicit bridge record can relate states when evidence supports the linkage. Aggregates do not create a project-specific bridge by themselves.

Settlement status is persisted independently from obligation/disbursement. `INSTRUCTION_RECORDED` or a disbursement observation cannot set a settlement row to `SETTLED`. A settlement row may be absent, unavailable, unverified, reversed, or contradicted according to source evidence. Those conditions remain distinct.

The domain `Payment` mapping must expose a state-specific read/write contract so a repository cannot accidentally update an obligation row when recording a disbursement or settlement. Amount equality is not identity or settlement proof.

## 9. Transaction Boundaries

### 9.1 Source ingestion transaction

One source snapshot ingestion transaction atomically records:

- snapshot metadata;
- source identifiers and raw observation metadata;
- normalized entity/event/state assertions;
- provenance attachments;
- contradiction/supersession links discovered in that batch;
- audit entry; and
- outbox messages for downstream processing.

Large payloads may be staged outside the transaction, but a snapshot is not visible as successfully ingested until its metadata and normalized records commit together. A failed batch must not appear as a complete observation.

### 9.2 Domain command transaction

A user or workflow command atomically updates the affected canonical/workflow records, increments the affected workflow `record_version`, records the audit event, and writes an outbox message. Projection refresh, notifications, and expensive reconciliation are asynchronous consumers and must be retry-safe.

### 9.3 Projection transaction

A projection worker consumes a committed outbox event and atomically writes the projection version plus its source canonical version/policy version. The outbox record has a stable message ID, aggregate/reference metadata, event type/version, creation time, publication/attempt state, and retry/error metadata. Reprocessing the same event is idempotent.

There is no transaction spanning an external source system and eGovTrace. External source success/failure is represented as an observation/result with explicit availability status.

## 10. Idempotency Implications

- Ingestion idempotency is scoped to a source snapshot and source record identity, with content hash/version checks where available.
- Replaying an identical snapshot produces no duplicate semantic assertion. A changed payload for the same source identity produces a new observation/version or contradiction, never an overwrite.
- Mutating commands use an idempotency key scoped to operation and caller/tenant boundary. A reused key with the same request returns the original result; the same key with a different request is rejected.
- Outbox delivery is at-least-once. Consumers deduplicate by message/event identity and make projection/workflow updates idempotent.
- Idempotency does not mean collapsing distinct source observations or financial states.

## 11. Concurrency Considerations

- Append-only source assertions avoid lost updates for observations.
- Mutable workflow records expose a `record_version` concurrency field. Writes must provide the expected version; a stale update is rejected and must be reread/reconciled.
- Unique constraints protect source snapshot/record identity and idempotency keys.
- Relationship adjudication and evidence availability transitions require version checks so two reviewers cannot silently overwrite one decision.
- Database transactions protect local invariants; they do not resolve conflicting source authorities. Conflicts remain queryable.
- Locking and isolation levels are implementation choices for T003.2 after workload and repository access patterns are known.

## 12. Migration Strategy

No migrations are created by T003.1.

When implementation begins, use versioned, reviewed, forward-only migrations:

1. expand with additive tables/columns and constraints that tolerate existing data;
2. backfill from synthetic fixtures or controlled data with provenance;
3. dual-read/dual-write only when a contract transition requires it;
4. validate counts, keys, provenance reachability, temporal preservation, and classification boundaries;
5. switch reads/writes;
6. contract/remove obsolete structures only in a later reviewed migration.

Every migration must be reversible at the data-contract level or have a documented recovery procedure. Historical source observations must be retained through migrations. No migration may reinterpret `UNAVAILABLE` as false, merge source IDs into eGovTrace IDs, or collapse financial states.

The first implementation ADR must select the migration tool and query/ORM approach. The tool choice must support typed access, explicit transactions, constraints, and migration review; it must not dictate domain semantics.

## 13. Test Strategy

Persistence implementation in T003.2 must add focused tests for:

- round-trip mapping of every current domain entity and value object;
- eGovTrace IDs remaining distinct from source identifiers and namespace collisions;
- duplicate snapshot/record replay and idempotent command replay;
- changed source payload creating a new version/contradiction rather than overwriting history;
- valid-time and observed/recorded-time queries, including as-of reads;
- provenance reachability from claim, relationship, event, financial state, and projection to source evidence;
- relationship basis/evidence retention, unresolved/rejected assertions, and weak identity not becoming confirmed;
- obligation, disbursement, and settlement separation, including instruction-not-settlement;
- `UNAVAILABLE`, `NOT_OBSERVED`, `ABSENT`, and `CONTESTED` remaining distinct;
- optimistic concurrency rejection for stale adjudication/workflow writes;
- atomic rollback of canonical state, audit record, and outbox message;
- at-least-once outbox delivery and projection deduplication;
- public projection exclusion of restricted evidence and internal assurance metadata;
- synthetic labeling and source-authority metadata;
- adversarial false joins, duplicate events, missing evidence, source outage, schema drift, and stale reviewer writes.

## 14. Proposed ADRs

### ADR-003 — Typed PostgreSQL Persistence Boundary

**Status:** Proposed.  
**Decision:** Use PostgreSQL relational tables as the V1 persistence boundary, with typed subtype records and relational graph assertions. Preserve source observations, temporal versions, provenance, and financial states as first-class records.  
**Rationale:** This matches ADR-002, supports transactional consistency and queryable evidence, and avoids a generic document or dedicated graph store becoming the semantic authority.

### ADR-004 — Append-Oriented Temporal and Provenance Records

**Status:** Proposed.  
**Decision:** Persist source observations, state versions, relationship assertions, provenance links, and financial-state records append-oriented; derive current/as-of views rather than overwriting history.  
**Rationale:** Historical evidence, reproducibility, contradiction handling, and source-authority boundaries require non-destructive persistence.

### ADR-005 — Transactional Idempotency and Outbox

**Status:** Proposed.  
**Decision:** Commit domain mutation, audit record, and outbox message in one local transaction; process projections asynchronously with idempotent consumers and optimistic concurrency for mutable workflows.  
**Rationale:** This provides reliable local state transitions without pretending an external source can participate in a distributed transaction.

## 15. Unresolved Questions / Explicit Non-Decisions

1. Which typed PostgreSQL query layer/ORM and migration tool will T003.2 select?
2. Which internal primary-key encoding is preferred after access-pattern testing: UUID, UUIDv7, or another opaque key?
3. Is PostGIS required in the first persistence slice, or can coordinates remain typed scalar fields until spatial queries are implemented?
4. What evidence object storage, retention, legal-hold, deletion/tombstone, and custody requirements apply beyond synthetic data?
5. What source registry fields and source-authority rules are required for each future connector?
6. What institution/tenant/purpose authorization predicates must be enforced at repository and database layers?
7. Which domain state families permit overlapping validity intervals, and which require explicit contradiction handling?
8. What exact public projection allowlist applies to each entity, relationship, evidence, and signal type?
9. What durable job runtime will consume the outbox in the modular monolith?
10. Which additional T002 entities from the broader build prompt are admitted into the first persistence slice, rather than inferred into the current model?

## 16. Recommended T003.2

Implement the smallest synthetic persistence slice for `Project -> Budget -> Procurement -> Contract -> Payment -> GovernmentEvent -> Evidence -> RelationshipAssertion`, using the selected typed PostgreSQL access/migration tooling.

T003.2 should produce:

- the ORM/query and migration ADR;
- initial schema migrations, but only then;
- repository interfaces that preserve the mappings and invariants in this document;
- transaction/idempotency/outbox behavior;
- provenance and relationship traversal queries;
- persistence integration and adversarial tests;
- a documented decision on key encoding, PostGIS use, evidence metadata, and projection boundaries.

T003.2 must stop if implementation pressure would require collapsing source IDs, temporal history, provenance, relationship evidence, financial states, or unavailable/negative statuses.
